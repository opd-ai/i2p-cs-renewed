# Development Roadmap
> Generated by goal-achievement analysis on 2026-05-04

## 📋 Project Context
**Purpose**: An experimental C# fork of i2p-cs that extends the upstream project with additional I2P protocol features, including post-quantum cryptography (NTCP2-PQ, MLKEM768-X25519), SSU2 transport, and a web-based router dashboard.  
**Target Audience**: Developers experimenting with I2P protocol implementations in .NET; acknowledged as "experimental" and "slop" — not intended for production use without further hardening.  
**Target Framework**: net10.0 (all projects)  
**Architecture**:

| Project | Role |
|---------|------|
| `I2PCore` | Core I2P protocol stack: crypto, transport (NTCP2/SSU2), tunnel layer, NetDB, session layer, client proxies |
| `I2CP` | I2CP (I2P Control Protocol) host implementation for external client connections |
| `I2PRouterWeb` | ASP.NET Razor Pages web dashboard for monitoring the router |
| `I2PRouterCli` | CLI entrypoint that wires up I2PCore + I2CP |
| `I2PCore.NTests` | NUnit 4 test suite (unit + integration tests) |

**Existing Quality Gates**: GitHub Actions CI workflow (`.github/workflows/dotnet.yml`) runs `dotnet restore`, `dotnet build`, and `dotnet test`. **However, the CI workflow specifies `dotnet-version: 5.0.x` while the solution targets `net10.0` — the CI has been broken since the framework upgrade and is not providing any actual quality gating.**  
**External Context**:
- BouncyCastle.Cryptography `2.7.0-beta.98` is a **pre-release** package; the current stable release is `2.4.0`. Using a beta in a cryptographic library is high risk.
- .NET 10.0 is a Standard-Term Support (STS) release; Microsoft will support it until May 2027. No urgency to migrate, but the framework is more recent than most CI tooling supports out of the box.
- Comparable I2P implementations (i2pd in C++, go-i2p, Java I2P) all provide fully functional SSU2 and ECIES-X25519 session encryption as core features, making these the baseline for a functional I2P router.

## 🚀 Prioritized Roadmap

### Priority 1: Fix SSU2 Session Handshake
**Why**: SSU2 is the primary UDP transport for modern I2P routers. i2pd and Java I2P default to SSU2 for most peer connections. A C# router unable to establish SSU2 sessions cannot participate fully in the network, directly blocking transit tunnel establishment and NetDB floodfill via new peers.  
**Current State**: SSU2 state machine code exists in `src/I2PCore/TransportLayer/SSU2/SSU2Session.cs` (1704 lines) and supporting files, but README explicitly marks both inbound and outbound as "Totally broken". Integration tests in `SSU2ConnectivityTests.cs` exist but require a live i2pd peer and cannot run in CI.  
**Required Changes**:
- [x] Instrument `SSU2Session.cs` with debug logging at each handshake state transition to identify where SessionRequest/SessionCreated/SessionConfirmed exchange fails
- [x] Compare `SSU2Host.cs` packet routing with the i2pd reference implementation (i2pd `SSU2.cpp`/`SSU2Session.cpp`) to find divergence in the Noise XK handshake
- [x] Verify that `SSU2SecurityValidator.cs` correctly validates headers before state machine transitions
- [x] Fix `SSU2AckManager.cs` if ACK handling is preventing the handshake from completing
- [x] Add offline unit tests in `I2PCore.NTests` that replay captured SSU2 handshake bytes (no live peer required)
- [x] Update `SSU2ConnectivityTests.cs` to assert specific protocol — currently it allows fallback to NTCP2 which masks SSU2 failures

**Success Criteria**:
- [ ] `TestCSharpConnectsToI2pd_SSU2` in `SSU2ConnectivityTests.cs` passes with SSU2 specifically (no NTCP2 fallback) against a local i2pd instance
- [ ] `TestI2pdConnectsToCSharp_SSU2` passes (inbound) — `TestI2pdConnectsToCSharp_SSU2` added but initiates an outbound connection; true inbound-only verification requires disabling NTCP2 outbound
- [x] At least 3 offline unit tests for SSU2 packet serialization/crypto round-trips pass in CI without a live peer

**Risk**: High — SSU2 failure is a complete protocol-level breakage, and the existing 1700-line session file will require careful state machine debugging.

### Priority 2: Fix Session Layer Encryption (ECIES-X25519 and MLKEM768-X25519)
**Why**: Both ECIES-X25519 and MLKEM768-X25519 garlic encryption are stated as "70%, doesn't work properly". These are the end-to-end encryption layer that every client interaction (HTTP proxy, server tunnels, streaming) depends on. All client-facing features are blocked at 60% until this is resolved.  
**Current State**: `src/I2PCore/SessionLayer/ECIES/ECIESSessionKeyManager.cs` (608 lines) and `Session.cs` (670 lines) implement the ratchet and tag management. Garlic routing is unit-tested in `GarlicTest.cs`, but session-level integration tests (`DataTransferTests.cs`, `EncryptionCompatibilityTests.cs`) require live network peers.  
**Required Changes**:
- [x] Add unit tests for `ECIESSessionKeyManager.cs` covering: new session tag generation, existing session tag lookup, and ratchet forward on `NextKey` block reception
- [x] Add unit tests for MLKEM768 key encapsulation round-trip in `src/I2PCore/Crypto/MLKEM/MLKEM768.cs` — also adds MLKEM512 and MLKEM1024 tests in `MLKEMTest.cs`
- [ ] Trace a complete garlic message from `ClientDestination.Send.cs` through `Session.cs` to `ECIESSessionKeyManager.cs` to find where the 70%→100% gap is (missing `LS2` re-inclusion? Wrong tag indexing?)
- [ ] Fix session key manager to correctly handle re-keying when the remote's `NextKey` block arrives
- [x] Add unit tests for `StreamingProtocolTest.cs` covering retransmission and window management (added: window flow control, ACK opens window, sequence number monotonicity, NACK handling, NACK packet round-trip)
- [x] Resolve CS0414 warning: `I2PStream._isTimeoutResend` at `src/I2PCore/SessionLayer/Streaming/I2PStream.cs:92` — either implement the resend timeout or remove the unused field

**Success Criteria**:
- [ ] `EncryptionCompatibilityTests.cs` echo test passes end-to-end against i2pd
- [ ] `DataTransferTests.cs` sends and receives at least 1KB of data via ECIES-encrypted garlic
- [x] Zero CS0414 warnings in `I2PStream.cs` — `_isTimeoutResend` field has been removed
- [x] `ECIESSessionKeyManager.cs` has unit test coverage for new-session path — 14 tests in `ECIESSessionKeyManagerTest.cs`; **existing-session and re-key paths are not yet covered** (see: [x] items below are new-session only)

**Risk**: High — This is the most complex cryptographic component; bugs here produce silent data corruption, not immediate crashes.

**Why**: Transit tunnel support (the "middle hop") is at 70%, but outbound endpoints and inbound gateways are broken. **Required Changes**:
- [x] Fix `GatewayTunnel.HandleReceiveQueue()` at `src/I2PCore/TunnelLayer/GatewayTunnel.cs:71` — add either `override` (if intentional polymorphism) or `new` keyword (if intentional shadowing); CS0114 warning indicates this virtual dispatch is currently broken
- [ ] Audit outbound tunnel endpoint packet handling against the I2NP spec — compare with `src/I2PCore/TunnelLayer/I2NP/Messages/VariableTunnelBuildMessage.cs` (613 lines) for message format correctness
- [ ] Add offline unit tests for `GatewayTunnel.HandleReceiveQueue()` that verify it processes a valid inbound tunnel data message without requiring a live peer
- [ ] Decompose `TunnelProvider.cs` (2380 lines) — extract tunnel build, tunnel maintenance, and tunnel selection into separate classes to make the code reviewable
- [x] Update `TunnelBuildTests.cs` to include at least one test verifiable without a live network (added `TunnelBuildRecordTest.cs` with 13 offline tests for serialization, flag checks, and reply record parsing)

**Success Criteria**:
- [x] CS0114 warning in `GatewayTunnel.cs` is resolved with the correct modifier (`private new` keyword applied to `HandleReceiveQueue()`)
- [x] `TunnelBuildTests.cs` has at least one test passing in CI without a live peer — `TunnelBuildRecordTest.cs` has 13 offline tests

### Priority 5: Reduce NTCP2 Memory Usage
**Why**: README explicitly calls out "+~300MB per 1000 active NTCP2 connections" as "bad" — this is a stated quality problem, not an inferred one. At 3700 connections, the router consumes 1.1 GB, making it unusable on typical server hardware.  
**Current State**: `src/I2PCore/TransportLayer/NTCP2/` contains 46 `new byte[]` heap allocations. Zero uses of `ArrayPool<T>`, `MemoryPool<T>`, or `ObjectPool<T>` exist project-wide. The `ReceiveNonce` and `SendNonce` fields in `NTCP2Session.cs` are CS0414 (assigned but unused), suggesting per-session buffers may be allocated but not managed correctly.  
**Required Changes**:
- [ ] Profile a test run with 100 NTCP2 sessions to establish a per-session baseline byte count (use `dotnet-trace` or VS profiler)
- [ ] Replace `new byte[]` receive buffers in `NTCP2Session.cs` with `ArrayPool<byte>.Shared.Rent()` / `Return()` pattern
- [x] Resolve CS0414 warnings: `NTCP2Session.ReceiveNonce` (line 84) and `NTCP2Session.SendNonce` (line 95) — either implement nonce tracking (replay protection) or remove the dead fields
- [ ] Use `System.IO.Pipelines` (`PipeReader`/`PipeWriter`) for the NTCP2 session receive loop to reduce buffer copying
- [ ] Add a memory benchmark test that asserts per-session overhead is under 200KB

**Success Criteria**:
- [ ] Memory usage drops below 150MB per 1000 NTCP2 connections (50% reduction from current 300MB)
- [ ] Zero CS0414 warnings in `NTCP2Session.cs`
- [ ] No regression in NTCP2 handshake success rate after pooling changes

**Risk**: Medium — Buffer lifetime errors (double-return to pool, use-after-return) are silent data corruption bugs; any pooling changes must be carefully tested.

## 🔍 Items Requiring Further Investigation

- **SSU2 exact failure point**: README says "Totally broken" but does not specify which handshake message fails. Recommend: add structured logging at each `SSU2Session` state transition and run against a local i2pd with packet capture (Wireshark + i2pd verbose logging) to identify the divergence.
- **ECIES-X25519 "doesn't work properly"**: The failure mode is unspecified — could be garlic decryption failure, session tag mismatch, or ratchet state corruption. Recommend: compare garlic message bytes exchanged with i2pd against the I2P ECIES spec (proposal 144) byte by byte.
- **MLKEM768-X25519 correctness**: The MLKEM implementation in `src/I2PCore/Crypto/MLKEM/` is custom C# code. Recommend: add NIST FIPS 203 test vector validation tests for the three key sizes (512, 768, 1024) before using in any real session.
- **HTTP Proxy "60% working"**: No specific failure cases are documented. Once session encryption is fixed (Priority 2), the proxy should be re-tested with a variety of .i2p destinations to catalog remaining failures (redirect handling, chunked transfer, keep-alive vs close semantics).
